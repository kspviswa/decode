OTel: an open telecom AI resource with 30 post-trained baselines and 16M downloads

Frontier models still struggle with telecom-specific tasks, so OTel (Open Telco) packages the missing substrate: derived datasets for retrieval, reranking, instruction tuning, and safety/abstention, plus 30 full-parameter post-trained baselines spanning embedding, reranking, and language models. As of May 2026 the released models had been downloaded over 16 million times with 157+ pieces of coverage worldwide.

Post-training lifts all three families: embedding retrieval reaches 93.5% NDCG@10, reranking reaches 0.952 MRR@10, and language-model correctness reaches 88.2%. OTel is framed as a reproducible starting point for telecom retrieval-augmented generation — with held-out evaluation partitions and context-grounded LLMs in one unified resource, it is a concrete foundation for grounding LLMs in 3GPP-grade domain data.

Why read it A direct lever for the LLM×telecom intersection: an open, post-trained telecom stack (embeddings, rerankers, grounded LLMs) plus data to build on. If you work on telecom retrieval or spec-grounded assistants, this is the foundation to extend rather than rebuild.

Scaling 5G-TSN bridges: operating regimes, scheduling, and time synchronisation under industrial traffic

3GPP Release 16 lets a 5G system operate as a transparent IEEE 802.1 TSN bridge, but its scalability under heterogeneous industrial workloads is poorly characterised. Using the nascTime framework on OMNeT++/Simu5G, this paper evaluates how many TSN endpoints a single 5G NR cell can bridge before per-flow quality-of-service degrades, modelling closed-loop control, machine vision, bulk telemetry, and IEEE 802.1AS traffic over a four-bearer architecture with 1 to 40 endpoints.

Three operating regimes emerge: below saturation non-DRR schedulers perform similarly; near saturation a quality-of-service-aware PF scheduler cuts critical-flow P99 latency by up to two orders of magnitude; under overload only QoS-PF keeps near-complete delivery for the highest-priority traffic. Isolating 802.1AS/gPTP on a dedicated high-priority bearer reduces clock-servo instability, and the evaluated sub-6 GHz 30 kHz-SCS configuration shows an effective latency floor around 2.25 ms — implying sub-3 ms TSN deadlines may need configured grants or higher numerology.

  A[5G NR cell as TSN bridge] --> B[Below saturation: schedulers similar]
  A --> C[Near saturation: QoS-PF wins by 2 orders]
  A --> D[Overload: only QoS-PF delivers]
Why read it Concrete numbers on how far one 5G cell can stretch as an industrial TSN bridge — scheduler choice and bearer isolation matter far more than raw bandwidth once you approach saturation. Useful sizing input for deterministic 5G deployments.

Autonomous cyber defense in connected vehicles: a three-tier multi-agent architecture for V2X security

A connected vehicle has roughly 100 milliseconds to decide whether an incoming Basic Safety Message is real or fabricated — a safety failure triggered by a security failure. This paper proposes a three-tier multi-agent architecture that treats that timing constraint as a hard design requirement: an onboard agent classifies each incoming V2X message into Accept, Drop, Quarantine, or Escalate within a 10 ms budget, deliberately biased toward Escalate when uncertain and passing ambiguous cases to a roadside edge agent rather than risking a dropped legitimate alert.

The edge tier works across a roadside-unit zone with a 50 ms budget, fusing threat assessments from multiple vehicles and resolving safety-security conflicts with complementary sensor observations; the cloud tier refines detection models through Byzantine fault-tolerant federated learning. Every latency budget derives from the 100 ms Basic Safety Message cycles mandated by SAE J2735 and ETSI EN 302 637-2, and the paper flags adversarial poisoning at the edge and missing regulatory frameworks as open problems.

Why read it Multi-agent security where the deadline is set by a safety standard, not a benchmark — a clean template for latency-budgeted, layered agent decisioning that generalises beyond connected vehicles.

Unsloth Dynamic 3.0 GGUFs: better top-1% accuracy at the same disk size for Qwen3.8-27B

Unsloth's Dynamic v3.0 quantization release targets Qwen3.8-27B, claiming more than 10% better top-1% accuracy at the same disk size than other providers' quants, backed by a new imatrix calibration set tuned for agentic coding, chat, and multilingual use. Everything is pure post-training quantization — no QAT, no QAD — and the imatrix is released for community reuse. Headline numbers include a 6.2 GB UD-IQ1_S that keeps roughly 72% of top-1% accuracy while being 89% smaller.

The quants work in llama.cpp and Unsloth Desktop, and the release is notable for publishing the calibration data alongside the artifacts. For anyone running open-weight models locally, this is a concrete claim about getting more retained quality per gigabyte at the same quantization level.

Why read it A directly usable quantization release with an unusually honest published calibration set. If you serve or run Qwen3.8-27B locally, the Dynamic 3.0 imatrix and quants are worth benchmarking against your current provider's build.

Qwen3.8-27B-DSpark-Agentic: a 1.36B draft model for speculative decoding on agentic workloads

A 1.36B-parameter DSpark speculative-decoding drafter for Qwen3.8-27B, trained from scratch on real agentic coding and assistant sessions rather than generic text. DSpark drafts a block of tokens conditioned on auxiliary features tapped from the target model's layers, with a Markov head for intra-block dependency and a confidence head that predicts per-position acceptance. A drafter never changes output — every drafted token is verified by the target — it only changes decode speed.

The model card reports a mean acceptance length of 2.88–2.92 on held-out agentic turns and 4.61 on GSM8K at DSpark block size 7, with 693 tokens/second aggregate decode at concurrency 8 on a single RTX PRO 6000 Blackwell. It is Apache-2.0, SGLang-compatible, and the training labels came from Qwen3.8-27B itself, so the whole pipeline is reproducible from open components.

Why read it A concrete, open speculative-decoding drafter aimed at the exact workload that dominates real agent runs — long agentic turns. If you serve open models for agent workloads, acceptance-length numbers like these directly translate into latency and throughput.
Ornith

Ornith-1.5: from self-scaffolding to a closed self-improvement loop

Ornith-1.5 extends the self-scaffolding idea into a closed self-improvement loop: the model proposes new tasks, generates task-specific scaffolds, and produces solution rollouts, with GRPO rewards flowing back into all three stages. Task reward is the product of validity, frontier difficulty (targeting roughly 20% success rate), and novelty against previously generated tasks, so the curriculum automatically gets harder as the model improves.

It ships at three scales — 397B MoE, 35B MoE (3B active), and a 9B mobile-tier dense model — with the 397B scoring 86.1 on Terminal-Bench 2.1, on par with Claude Opus 4.8, and outperforming GLM-5.2 and DeepSeek-V4-Flash-0731. The 9B model, with a quantized mobile version, is deployable on phones while beating much larger models like Gemma 4-31B and Qwen 3.6-35B on agentic coding.

Why read it One of the more complete demonstrations of end-to-end self-improvement — the model writes its own tasks, harnesses, and rollouts, and rewards feed back into all three. If you follow self-improving and agentic training loops, this is the current state of the art in open models.

SPADE: self-play in adaptive synthetic executable environments for open-ended self-improvement

Continuous self-improvement needs an ever-expanding pool of self-generated, adaptive goals, but existing training pools keep the goal distribution fixed as the learner scales. SPADE is a self-play RL framework where a single LLM plays two roles: an Environment Designer that writes complete, long-horizon training environments as executable code with an OpenAI Gym-style reset()/step() interface, and a Reasoning Agent that learns to act in them, spanning reasoning problems and multi-step agentic tool use in one interface.

The Reasoning Agent's regret — the gap between reward with and without privileged hints — drives the Environment Designer to target environments at the edge of the agent's capabilities while keeping them feasible. Scaling to 30B parameters, SPADE improves over the strongest fixed-environment baseline by +5.3 on average across eight held-out math, science, code, and reasoning benchmarks, and lifts tool use by +5.7 on BFCL-v4 multi-turn and +13.9 on ACEBench-Agent.

  E --> R[Reasoning Agent]
  R -->|rollouts + regret| D
Why read it Makes environment design itself a learnable component, so the curriculum co-evolves with the agent. A strong, concrete datapoint for open-ended self-improvement that complements the Ornith-1.5 release.

What is missing from AI post-training AI: an empirical analysis of agent-run training loops

LLM agents can now post-train an LLM end-to-end — writing code, launching training, and evaluating checkpoints — but this paper argues the field conflates two distinct capabilities: execution-level iteration within a chosen strategy, and strategy-level revision as evidence accumulates. Analyzing a large corpus of publicly released post-training trajectories, the authors find that agents lock in their training strategy at the very start and spend the entire remaining budget on local adjustments.

In other words, the systems are good at executing a plan but poor at revising the plan itself when results come back. It is a sharp empirical caution for anyone building self-improving training pipelines: the bottleneck is not running the steps but re-deciding the strategy mid-run.

Why read it A clean diagnostic for a gap that matters as agentic training loops mature — the ability to revise strategy, not just iterate within it. Directly relevant if you build or evaluate agents that train models.

apex-inference-chip: an open LLM inference chip on FPGA, bit-exact against a golden model

This repo implements one transformer decoder layer in RTL for Qwen2.5-0.5B and runs the real model on an FPGA at a measured 0.56 tokens/second — every silicon value bit-exact against a golden software reference, with a claimed 140× speedup over the initial naive version. The full evidence trail (waveforms, bit-exact checks, power numbers) is in the repo, making it an unusually honest hardware deep-dive.

The architectural bet is that the KV cache is the growing memory bottleneck, so it compresses keys and values in-datapath (per-channel INT4 keys, per-token INT4 values, an fp16 outlier lane) the moment they are produced. It is one tile rather than a full chip, sized for 7B-class models in the paper architecture, and it is the rare open project that shows an actual LLM executing on custom silicon rather than just a simulator.

Why read it A rare, verification-first account of running an LLM on real silicon, with the KV-compression story made concrete in hardware. If you care about edge inference or custom accelerators, this is the honest engineering reference.

NVFP4 on Volta: running Qwen 3.8's Blackwell-era format natively on four 2017 V100s

A r/LocalLLaMA post claims to run Qwen 3.8 in NVFP4 — a format built for Blackwell hardware — natively on four 2017-era V100s, reportedly matching the author's $6,000 RTX 5090 on single-request decode. The V100s ran Qwen3.8's published mixed FP4/FP8 weights directly, without an emulation layer.

If the numbers hold up, it is a striking example of extracting frontier-era quantization from eight-year-old hardware, and a good sanity-check on what the 4-bit format war actually costs in practice. Community threads like this are worth reading as a counterweight to vendor claims about which GPUs can run which formats.

Why read it A concrete data point on whether the newest quantization formats are really locked to the newest silicon — relevant for anyone sizing local inference on older, cheaper GPUs.

PostgreSQL for everything: the one-database consolidation argument

An essay arguing that PostgreSQL quietly replaces a surprising amount of the modern stack: Solr/Elasticsearch for full-text, MongoDB for jsonb, Kafka/RabbitMQ via SKIP LOCKED queues, ClickHouse via TimescaleDB, Redis via unlogged tables, the filesystem, graph databases via ltree, and even microservice middleware — with pgvector and pgai covering AI retrieval workflows.

The message for builders is a consolidation reflex: before adding shiny technology X, ask whether Postgres can already do it. It is a practical, opinionated guide to the one-database era that resonates with the cloud-native instinct to reduce moving parts.

Why read it A pragmatic consolidation playbook that maps familiar workloads onto a single database, including the AI retrieval layer via pgvector/pgai. If you lean toward fewer moving parts in your stack, this is a useful checklist.
